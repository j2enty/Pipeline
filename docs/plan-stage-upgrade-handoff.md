## 0. 한 줄 요약

`/plan`을 **"한 방에 문서 생성"에서 "①의도캐기 → ②AI용 명세 → ③완결성 critic → ④사람용 파생 → ⑤정합성 critic → ⑥사람 게이트"의 6단계 파이프라인**으로 승격한다. 핵심은 **사람용/AI용 문서 2층 분리**와 **영역 간 공유 계약 문서**다.

## 0.5. 확정 결정 로그 (2026-06-01 Pipeline 세션) ★ 최신

> 핸드오프 설계를 Pipeline 세션에서 검토하며 운영자와 확정한 결정. **원안(§3.5·§8)보다 이쪽이 우선.** 구현 착수 전 이 블록부터 반영할 것.

### D1. critic 검증 강도 = **비대칭 (원안 §3.5 "단일 1패스 시작"을 대체)**
- 근거: Pipeline CLAUDE.md·운영자 메모리의 *"단일 모델 리뷰는 과신, Claude+Codex 이중 필수"* 원칙은 코드에 적용되는데, plan은 자동화 품질의 **상한선이자 유일한 사람 게이트**라 코드와 같거나 더 높은 기준을 받아야 함. 원안의 "단일 1패스"는 제일 중요한 산출물에 제일 약한 검증을 붙이는 자기모순.
- 결정:
  - **③ 완결성 critic = 단일 모델** (중간 검사, 싸게)
  - **⑤ 정합성 critic = 이중 모델 (Claude + Codex 교차)** — "사람이 GO 누르기 직전 마지막 방어선"이라 여기에 교차를 몰아 비용 대비 안전마진 최대화
- → §8-2 부분 해소. 남은 것: 이중 critic을 config 토글로 끌 수 있게 할지(비용 회피)는 미정.

### D2. 단계 합격 판정 = **골든 픽스처(모범답안 시험지) 방식**
- 배경: plan 산출물은 글이라 "테스트 초록불"이 안 나옴. 그러나 Pipeline 작업 프로토콜은 단계별 테스트 게이트를 강제 → 글에도 합격선이 필요.
- 방식: 실제 이슈를 입력으로 넣고, "사람용에 반드시 떠올라야 할 항목"을 정답으로 박아 대조(프론트 스냅샷 테스트와 동형). 어긋나면 불합격.
- **개수가 아니라 "사고 종류"별로 1장씩** 설계 (각 픽스처가 서로 다른 실패 모드를 노림):
  | 막을 사고 | 픽스처 |
  |---|---|
  | 구멍(rate-limit·인증 누락) | `service-status-page` (착수 케이스) ✅ |
  | 뻔한 소리(일반론 도피) | 일부러 애매한 이슈 → 캐묻고 깊이 파는지 |
  | 조용한 기정사실화 | 결정거리 숨은 이슈 → "★ 결정할 것"으로 떠오르나 |
  | 영역 간 어긋남(snake/camel 등) | 2+영역 이슈 → 계약서가 맞춰주나 |
- **착수는 `service-status-page` 1장.** 나머지는 한 번에 만들지 말고 **해당 기능 구현 시 함께 추가**(가정+표시 기능 ↔ 기정사실화 픽스처, contract.md 기능 ↔ 영역 어긋남 픽스처). 컴포넌트와 테스트를 같이 짜는 원리.

### D3. 픽스처 고도화 = **실전 빵꾸 → 박제 (피드백 루프)**
- 처음 4종 이후 픽스처는 손으로 늘리지 않고 실전에서 자라게 함: 실제 plan 실행 → 사람 게이트에서 빵꾸 발견 → 그 케이스+기대출력을 픽스처로 추가 → 그 사고 영구 차단(회귀 테스트와 동형).
- **최고 가치 픽스처 = ⑤ 이중 critic이 둘 다 통과시켰는데 사람이 게이트에서 잡은 것** — 정확히 기계 사각지대라 다음부터 검사원이 그 사각을 보게 됨.
- 인프라 재활용: 기존 finding 추적 회로(`major-issue`/`minor-issue`)에 plan 게이트 빵꾸도 흘려보내 픽스처 후보를 자동 적재.
- 두 축: ①개수(실전 빵꾸→새 픽스처) ②기준(설계가 좋아질수록 기존 픽스처의 정답 눈높이도 상향).

### D4. 역할 분리 재확인 (D2·D3의 전제)
- **픽스처 = 기계(공장) 회귀 감시** / **사람 게이트(⑥) = 의도 판단** — 처음 보는 새 기능이 "내 의도와 맞는지"는 기계가 판정 불가라 ⑥은 없앨 수 없음. 설계 철학(*"정합성 검증=기계, 의도 검증=사람"* §3.2)과 동일.

### D5. 구현 전략 = **빅뱅 금지, 싸고 효과 큰 것부터 단계적**
- 현 `plan.md.tmpl`(408줄)의 Step 7~10은 race condition 가드·멱등성·sub-issue API 함정 등 검증된 운영 배관 → 앞단(Step 4~6) 개편이 뒷단을 깨지 않도록 보수적으로.
- 저비용·고레버리지 항목(가정+표시 / "안 하는 것" 섹션 / 7구간 인터뷰)을 contract·이중critic 없이 **선행 적용 가능** → 여기부터. 각 기능은 자기 픽스처와 함께 출하(D2).

### D6. 인터뷰 구현 = **plan.md.tmpl 자체 내장 (별도 플러그인·스킬 비종속)** — §8-1 해소
- 근거: 인터뷰 "엔진"은 거창한 코드가 아니라 **프롬프트**(질문지 + 꼬리질문 지시 + 종료판정 지시)일 뿐이라 자체 내장 비용이 낮음. 무거운 라이브러리 import 대신 `if(빈칸) 다시 물어` 몇 줄로 끝나는 것과 동형.
- 결정: 기존 `oh-my-claudecode:deep-interview` **스킬 호출을 제거**하고, 7구간 대본(D7)을 plan.md.tmpl 안에 직접 기술한다. (원안 §8-1의 (b) 자체 루틴.)
- 효과: Pipeline의 종속성 제로·오픈소스화 목표(§6.3 OMC 의존 우려)를 **인터뷰 부분에서 선제 제거.**
- 범위 주의: `planner`·`critic` 에이전트는 여전히 OMC 의존(§6.3 그대로, 별도 범용화 과제). 이번 탈종속은 **인터뷰 한정.**
- 잔여: `--deep` 플래그의 위치 재정의(§8-4)는 별도. 7구간이 기본이 되면 `--deep`이 뭘 의미하는지 따로 정한다.

### D7. 7구간 대본 개정 (§3.3 원안 대체) — §2의 "조용한 기정사실화" 3약점 커버
세 변경 모두 한 뿌리: **AI가 결정을 조용히 사실처럼 박는 것 차단.** 운영자가 비전문 영역일수록 AI가 빈칸을 가정으로 채우되 *반드시 표시*해 ⑥ 게이트에 걸리게.

```
1. 뭘 만들려는 거예요? (한 문장, 전문용어 빼고)          ← Heilmeier Catechism
     └ 답이 흐리면: "왜 필요해요?" → "왜요?" 캐물음       ← 5 Whys (뻔함 방지)

2. 지금은 어떻게 하고 있고, 뭐가 불편해요?               ← Heilmeier

3. 누가 써요? 성공하면 뭐가 달라져요?                    ← Heilmeier (= 성공기준)

  [신설 ◀약점2] 접근법 노출
  3.5 이거 만드는 방법이 여러 개일 텐데, 생각해둔 방식 있어요?
      └ 없다고 하면: AI가 후보 2~3개 깔고 "○○ 방식으로 갈게요 ← 맞나요?"
      → '아무 방식이나 골라 사실처럼 박는 것' 차단. 접근법도 결정임 → 사람용 ★결정할것로.

4. 이번엔 뭘 '안' 해요? 다음으로 미루는 건?              ← MoSCoW "Won't" (= 경계)
   [◀약점3] 스킵 금지 — 이슈에 거의 안 적혀 있음. 거의 항상 물어라.

  [개편 ◀약점1] 5번을 '열린 질문'에서 'AI 선제 가정'으로
  5. (❌ "보안·성능·제약 있어요?" 식 열린 질문 금지)
     AI가 표준 제약을 먼저 깔고 확인받는다:
       "보통 이런 기능은  · 인증: ___  · rate-limit: ___  · 입력검증: ___
        으로 갑니다. 이대로 가정할게요 ← 맞나요?"
     → 운영자가 "딱히 없어요" 해도 빈칸이 아니라 '가정+표시'로 사람용 ★결정할것에 박힘.
     [◀약점3] 이것도 스킵 금지 (서버 비전문 운영자일수록 필수).

6. 제일 위험한 게 뭐예요? 아직 모르는 건요?              ← Heilmeier (= 리스크)

7. "이미 출시했다 치고" 한 줄로 말하면?                  ← Working Backwards (= 한 줄)
```

- **약점1(5번 개편)**: 열린 질문 → AI가 표준 제약(인증·rate-limit·입력검증) 선제시 + "이대로 가정할게요 ← 맞나요?". 비전문 운영자의 "딱히요"가 빈칸→기정사실화로 새는 경로 차단. (3대 약점 중 최우선.)
- **약점2(접근법 프로브 신설, 3.5)**: Heilmeier의 "왜 이 접근?"이 원안에 누락됐던 것 보강. AI가 구현 방식을 임의 선택하고 사실인 척 박는 것 차단.
- **약점3(스킵 바닥선)**: 적응형 스킵은 유지하되 **4번·5번은 스킵 금지**(이슈에 거의 부재). AI가 이슈의 옅은 언급을 "답 있음"으로 성급 판정하는 것 방지.
- 유지(잘 된 점): 1번("만들려는 것")↔7번("출시했다 치면")은 **시작 인식 vs 완성 모습의 차이**를 드러내는 의도된 북엔드 중복.

### D8. `--deep` 플래그 재정의 (§8-4 해소)
- 배경: D7로 7구간 인터뷰가 **기본**이 되면서, 기존 `--deep`(deep-interview 풀 인터뷰)의 자리가 사라짐.
- 결정: **기본 = 7구간 적응형**(D7대로 이슈에 답 있으면 스킵, 단 4·5번은 항상 물음) / **`--deep` = 스킵 끄고 7개 전부 + 꼬리질문 강화.**
- 근거: D7 대본에 이미 적응형 스킵이 내장돼 평소엔 자동으로 짧아짐 → 사소한 이슈의 인터뷰 피로 최소화. 중요한 기능에서만 `--deep`으로 풀 인터뷰 강제. 귀찮음(가벼움)·꼼꼼함(깊이)을 한 플래그로 양립.
- 주의: `--deep`은 더 이상 `deep-interview` **스킬 호출이 아님**(D6). 같은 7구간 대본을 "스킵 없이" 도는 모드일 뿐.

### D9. ⑥ 사람 게이트 = **Docs PR 승인을 게이트로 (§8-5 해소)** — ⚠️ **전제 오진단 발견, 아래 R1 [정정] 참조. 최종 처리 보류 중.**
- 문제(현행 구멍): 현 `plan.md.tmpl`은 사람용 PR을 올리면서 **동시에** sub-issue를 Step 8에서 **즉시 Status=Ready**로 올림 → 운영자가 기획서를 읽기도 전에 `/kickoff`가 돌 수 있음. 문은 열려 있는데 **잠기지 않은** 상태 → "plan이 유일한 게이트"라는 핵심 철학이 실제로는 미작동.
- 결정: **사람용 기획서 Docs PR의 승인(머지)을 ⑥ GO 게이트로 삼는다.** 승인 전에는 sub-issue를 Ready로 올리지 않아 kickoff를 **실제로 차단**한다.
- 근거: ①PR이라는 잠금장치가 이미 존재(신규 비용 0) ②운영자 Slack 계획(Ready 검증 모바일화)과 접합 — PR 승인을 추후 Slack 버튼으로 외화 가능 ③Pipeline App-native chain 철학과 합치(아래 control flow).
- **★ control flow 변경 (구현 시 핵심 — D5 보수성 주의 대상)**:
  - 현행: Step 6(Docs PR) → Step 7(sub-issue 생성) → Step 8(즉시 Ready) 가 **한 run 안에서** 완결.
  - 변경: sub-issue는 생성하되 **Ready가 아닌 보류 상태(예: Planning/Backlog)**로 둠. **"plan PR 머지됨" 이벤트를 App이 수신 → sub-issue를 Ready로 전환**(게이트가 자동 회로의 한 마디가 됨). 즉 plan은 한 run에 안 끝나고 사람 승인 지점에서 멈췄다 재개.
  - 영향 범위: Step 8(Status 세팅)의 시점 분리 + App chain 핸들러 신설. Step 7의 sub-issue/링크 배관(race 가드 등)은 유지.
- 잔여: 보류 상태를 Planning으로 둘지 Backlog로 둘지, App chain 핸들러를 신규 yml로 뺄지는 구현 플랜에서 확정.

### R1. 구현 착수 전 아키텍트 적대적 검토 결과 (2026-06-01) ★ Phase A 착수 보류
독립 아키텍트(읽기 전용 Opus)가 Phase A 플랜을 적대적 검토. 셀프 승인 방지용. 착수 전 선결 사항:

**[치명·선결] Phase 0 안전 테스트 경로 신설.** `plan.md.tmpl`은 실행 시 **실제 GitHub 변경**(Step 6 `gh pr create` / Step 7 `gh issue create`+sub_issues / Step 8 Project mutation / Step 9 parent 본문 변조)을 일으키는 지시문 → G-1/G-2 골든 픽스처를 **실레포 오염 없이 돌릴 방법이 현재 전무.** Pipeline 프로토콜의 "단계별 테스트 게이트"가 원천 성립 불가. 해결책(셋 다 채택):
- `--dry-run`을 **쉘 분기로 코드화**(LLM 재량 제거 — "실행하지 마" 지시문은 비결정적). 부수효과(`gh`) 명령을 Step 6~9 끝 **단일 "원격 반영" 블록**으로 모으고 진입부에서 `if [ "$DRY_RUN" = true ]` **1회 분기**(안전망↔단순성 양립, §3.2 canonical 생성→검증→반영 구조와 합치).
- 사람용 문서는 dry-run에서도 **로컬 write**(G-1 검증 대상), push/PR만 스킵.
- `--issue-fixture <path>`로 이슈 입력 격리(실 이슈 조회 우회, 외부 상태 비의존).
- 메타테스트: dry-run 후 `gh pr list`/`git log` 무변화 assert.

## 1. 배경 — 왜 plan을 고치나

### 전제
- **파이프라인의 핵심 = plan.** 자동 실행 회로(kickoff→review→merge)는 plan을 충실히 따르는 기계라, **plan의 품질이 전체 자동화 품질의 상한선**이다. plan이 틀리면 자동 회로가 "틀린 걸 빠르고 정확하게" 만든다.
- plan은 **운영자가 손대는 유일한 인간 게이트.** 레버리지가 100% 실리는 지점.
- 목표: **"사람이 보기 좋은 기획서" + "AI가 개발하기 좋은 문서"를 동시에** 만든다.

### 현재 `/plan`의 실측 불만 (3가지)
1. **뻔한 소리만 한다** — 코드베이스를 깊이 안 읽고 일반론으로 도망감. 결정을 회피.
2. **사람이 읽기 어렵다** — 한 문서가 사람·AI 두 청중을 동시에 섬기려다 잡탕이 됨.
3. **구멍이 계속 있다** — 쓴 다음 아무도 검증을 안 함. + 결정거리를 자명한 사실처럼 평평하게 깔아서 운영자 레이더에 안 걸림.

→ 이 셋은 한 뿌리: **plan이 단발(one-shot) 생성**이라서다. 고도화 = 단발을 다단계 파이프라인으로 + 문서를 청중별로 분리.

## 2. 역할 경계 — Pipeline 원칙과의 정합 ★ (먼저 읽을 것)

이 설계의 메타 원칙은 Pipeline CLAUDE.md의 **"프로젝트 종속성 제로 + 설정 주입"** 과 **완전히 일치**한다.

| | 파이프라인 = How (범용 엔진, 본체) | 프로젝트 = What (주입) |
|---|---|---|
| 무엇 | plan 6단계·2층 분리·인터뷰 대본·critic·계약문서 패턴·SSOT 수렴 메커니즘 | 영역 목록(Backend/Admin/…)·SSOT 문서 경로(예: `ARCHITECTURE.md`)·도메인 판단 |
| 어디 | `plan.md.tmpl` 템플릿 로직 (placeholder/config) | `pipeline-config` + `__PLACEHOLDER__` 치환 |

**채택 모델 = Convention over Configuration** (ESLint `recommended` preset 비유):
- 파이프라인은 좋은 관행을 **의견 있는 기본값으로 제공**, 각 프로젝트가 config로 **켜고 끔(opt-in/out)**.
- **정적**: 프로젝트가 config에 "인터뷰 쓴다 / 계약문서 쓴다 / SSOT 수렴 안 쓴다" 선언.
- **능동**: plan 실행 시 프로젝트 특성(예: 영역 수)을 보고 "이거 켜는 게 좋아요, 켤까요?" 제안 → 수락 시 config에 저장(한 번만 물음).
- **기본값 철학 = C 혼합**: 가벼운 관행(인터뷰·2층분리·계약문서)은 **기본 ON**(끌 때만 명시), 무겁고 되돌리기 비싼 것(ARCHITECTURE 수렴 자동화)만 **능동 제안으로 확인**.

> **주의(설정 지옥 방지)**: 토글을 잘게 쪼개되 기본값을 의견 있게 둔다(대부분 켜진 채, 끌 때만 명시). 능동 제안은 한 번 결정하면 config에 저장해 매번 묻지 않는다.

> **흥미로운 정합**: 이 "파이프라인이 제안 → 프로젝트가 결정" 구조는, plan 내부의 "AI가 가정 → 사람이 게이트" 패턴(§3.6 가정+표시)의 한 층 위 재현이다. 같은 철학이 두 레벨에서 반복된다.

## 3. 목표 설계 전체

### 3.1 두 층 분리 (청중이 둘이다)

하나의 문서로 사람·AI 둘 다 만족시킬 수 없다. 청중별로 분리한다.

| | 사람용 (`requirements/`) | AI용 (`plans/`) |
|---|---|---|
| 청중 | 운영자(리뷰어) | executor(구현자) |
| 담는 것 | **왜**·결정·트레이드오프·리스크 | **정확히 무엇을**·인터페이스·검증기준 |
| 형태 | 보고서, 짧고 시각적, 스캔 가능 | 명세, 길어도 됨, 모호함 0 |
| 운영자가 읽나? | **이것만 읽고 GO** | **안 봐도 됨** |

> 현재 `plan.md.tmpl`도 두 파일(`requirements/<slug>.md` + `plans/<slug>-<영역>.md`)을 만든다. **구조는 이미 있으나 각 문서의 청중·역할이 정의 안 돼서 둘 다 어중간하다.** 이 설계는 그 역할을 못 박는 것.

### 3.2 6단계 파이프라인

```
① 의도 캐기        인터뷰로 운영자 의도 끌어냄                → 뻔함 방지
② AI용 명세 작성    코드베이스 깊이 읽고 결정 내림 (canonical 원천)
③ 완결성 critic    "뭐가 빠졌나/모호한가/영역 간 안 맞나"      → 구멍 방지
④ 사람용 요약 파생   ②에서 GO/수정 판단 바꾸는 것만 추출         → 가독성
⑤ 정합성 critic    사람용 = AI용 대조 (운영자가 못 하는 검증)   → 정합성 보장 ★
⑥ 사람 게이트       운영자가 사람용만 읽고 GO or 수정
```

**중요 — canonical 흐름**: AI용 명세(②)가 원천이고, 사람용(④)은 거기서 **추출/압축한 뷰**다. 같은 원천에서 나오므로 정합성이 구조적으로 받쳐진다. (현재 plan은 영역 플랜을 먼저 만들고 기획서는 별도 요약 — 순서/관계를 이 canonical 구조로 재정의)

**검증을 두 종류로 분리 (정합성 문제 해결)**:
- 운영자 우려: *"사람용 보고 GO 했는데 AI용엔 딴 게 들어가 있으면 못 거른다"*
- **의도 검증** ("내가 원하는 방향 맞나?") → **사람만** 가능 → 운영자가 사람용으로(⑥)
- **정합성 검증** ("사람용 = AI용인가?") → **기계** 가능 → ⑤ critic이
- 비유: 사람용=인터페이스 선언, AI용=구현, ⑤=contract test. 인터페이스만 봐도 안심하는 이유.

### 3.3 ① 인터뷰 7구간 대본 (확정) — ⚠️ **§0.5 D7로 개정됨. 구현 시 D7 대본 사용. 아래는 원안(근거 참고용).**

뻔함의 근원은 "이슈에 적힌 게 AI가 가진 전부"라서다. 인터뷰로 의도 간극을 메운다. **외부 검증 방법론을 조합한 고정 대본** (입문 운영자도 그대로 따라할 수 있게):

```
1. 뭘 만들려는 거예요? (한 문장, 전문용어 빼고)        ← Heilmeier Catechism
     └ 답이 흐리면: "왜 필요해요?" → "왜요?" 캐물음     ← 5 Whys (뻔함 방지)
2. 지금은 어떻게 하고 있고, 뭐가 불편해요?             ← Heilmeier
3. 누가 써요? 성공하면 뭐가 달라져요?                  ← Heilmeier (= 성공기준)
4. 이번엔 뭘 '안' 해요? 다음으로 미루는 건?            ← MoSCoW "Won't" (= 경계, 구멍 방지)
5. 보안·성능·기존 시스템 제약 있어요?                  ← 결정거리 캐기 (예: 인증)
6. 제일 위험한 게 뭐예요? 아직 모르는 건요?            ← Heilmeier (= 리스크)
7. "이미 출시했다 치고" 한 줄로 말하면?               ← Working Backwards (= 사람용 "한 줄")
```

- **적응형**: 이슈에 이미 답이 있는 질문은 건너뜀. 간극만 묻는다.
- **질문 하나씩**, 종결 후 다음 (운영자 커뮤니케이션 선호).
- **종료 조건**: 모호성이 임계 이하로 떨어지면 멈춤(모호성 게이팅).
- **최대 개선 지점**: 4번(안 할 것)·7번(한 줄)이 현재 plan에 **완전히 빠져 있음.** 여기서 가장 큰 도약이 나온다.
- **현재 코드와의 관계**: 현 `plan.md.tmpl`은 `--deep` 모드에서 `oh-my-claudecode:deep-interview`를 호출한다. 운영자는 deep-interview를 이미 많이 쓰고 있어 **다른 방법론 기반(위 7구간 대본)**을 원한다. → 구현 시 deep-interview에 이 대본을 주입하든, 자체 대본으로 가든 §8에서 판단.

### 3.4 ② AI용 명세 + 영역 간 공유 계약 문서 (확정)

**의외의 발견**: 현재 AI용 문서(`plans/<slug>-<영역>.md`) 자체 품질은 이미 괜찮다(태스크 분해·완료기준·리스크까지). ②의 진짜 과제는 **영역 간 계약**이다.

**문제**: 같은 API를 영역마다 따로 서술해서 어긋난다. (backend는 `db_status` 제공, admin은 `dbStatus` 기대 → 영역별 구현은 각각 "통과"인데 합치면 안 맞음. cross-repo의 약한 고리)

**해결 = 공유 계약 문서 분리**:
```
② 산출
  ├─ {번호}-{slug}-contract.md   ← cross-cutting 계약 SSOT (API 스키마·데이터 모델·이벤트·공통 규약)
  ├─ {번호}-{slug}-backend.md    ← 계약 *참조* + 구현 태스크
  ├─ {번호}-{slug}-admin.md
  └─ {번호}-{slug}-frontend.md
```
- 모든 영역이 같은 계약을 보므로 **어긋날 수 없음**.
- **조건부**: 2개 이상 영역이 인터페이스로 만날 때만 생성. 단일 영역이면 생략(오버헤드).

**② 내부 순서 (인터페이스 우선)**:
```
②a. 코드베이스 흡수 (프로젝트 SSOT·기존 패턴·메모리 깊이 읽기)  → "뻔함" 방지
②b. 계약 먼저 작성 (contract.md)
②c. 영역별 구현 명세 (계약 참조)
```

**단점 & 완화** (정직하게 기록):
| 단점 | 완화 |
|---|---|
| 표류 (계약 문서 vs 실제 코드 어긋남) | **SSOT 수렴 순환** (§7) |
| 과잉 선행 동결 (waterfall) | 계약은 그 기능의 스냅샷일 뿐, 구현 학습이 SSOT로 되먹임 |
| 단일원천 = 같이 틀릴 위험 | ③ critic이 계약 자체도 검사 |
| 입도 판단 부담 | "영역 간 만남 여부" 기준으로 계약 vs 영역 문서 분리 |

### 3.5 ③⑤ critic (확정)

**메커니즘**: AI 에이전트(예: OMC `critic` — work plan 리뷰 전문)를 plan 스킬 안에서 시점 다르게 호출. PR을 보는 `/review` 회로와 **별개** — 대상이 *plan 문서*다.
- ② AI용 명세 작성 → ③ critic이 AI용 검사 (구멍)
- ④ 사람용 파생 → ⑤ critic이 사람용↔AI용 대조 (정합성)
- 비유: ③ = 린터/타입체커, ⑤ = contract test

**핵심 원칙 — critic은 "메우지 않고 분류한다"** ★ (이거 반드시 지킬 것):
- critic이 구멍을 다 알아서 메우면 → "조용한 기정사실화"가 critic 버전으로 재발한다(§4 `인증 없이` 사건).
- **표준 누락**(rate limit·입력검증·에러처리 등 자명) → ② 명세에 보강 제안 + 사람용에 "○○로 가정 ← 맞나?"로 표시
- **판단 필요**(가치 결정, 예: 인증 공개 여부) → **자동 결정 금지** → 사람용 `★ 결정할 것`으로 올림
- 즉 critic = "자동보강 가능 / 사람결정 필요"를 가려내는 **문지기**. 메우는 게 아니다.

**체크리스트**:
- ③ 완결성: 표준 보안 누락(인증·rate limit·입력검증) / 에러·경계 처리 / 영역 인터페이스 정의됐나 / acceptance 검증가능성 / 모호어("적절히") / 인터뷰 제약 반영
- ⑤ 정합성: 사람용 ★·키피처·안하는것 ↔ AI용 일대일 대응 / AI용에 미승인 중대결정 없나 / 사람용 가정이 AI용에 반영됐나

**🟢 추가 2종 (확정)**:
- **영역 교차 critic**: 영역별 명세의 인터페이스 서술 상호 일치 검사 (필드 표기 snake/camel·응답규약·CORS 등). 계약 문서(§3.4)가 있으면 "각 영역 vs 계약 1:1"로 단순해짐.
- **인터뷰 의도 추적**: ① 인터뷰 답 → ② 명세 → ④ 사람용 추적성 검사. 의도가 중간에 증발·변질 안 했나 보증.

**시작 범위**: 단일 critic · 1패스로 시작. 구멍이 새면 강화 (🟡 적대적 다수 critic / 반복 루프). ⚪ 나중(과잉): slicing 체크 / critic 노트 로그 / 운영자 ★판단 패턴 학습.

### 3.6 ④ 사람용 문서 템플릿 (확정)

각 섹션이 ① 인터뷰 7구간과 맞물린다.

```markdown
# {번호} {제목}

## 한 줄
{무엇을·왜 — "아 이거구나"가 한 문장에}     ← 인터뷰 1·7번 (Working Backwards)

## 당신이 결정할 것  (★ = 되돌리기 비쌈)
- ★ {보안/아키텍처/출범급 결정}              ← 인터뷰 5번
- {AI 가정}: "○○로 가정함 ← 맞나요?"        ← 가정+표시 (인터뷰 답 없이 채운 것)

## 이번에 안 하는 것 (경계)                    ← 인터뷰 4번 (Won't)
- {다음으로 미루는 것 — scope 밖}

## 키 피처
- {핵심 기능}                                 ← 인터뷰 3번

## 리스크 / 미정 (구멍)
- {안 정해진 것·노출·한계}                    ← 인터뷰 6번

## 상세 명세 → plans/{번호}-{slug}-*.md  (AI용, 안 봐도 됨)
```

**핵심 장치**:
- **편집 기준** = **"이 정보가 운영자의 GO/수정 판단을 바꾸는가? 아니면 뺀다."** 키 피처·되돌리기 비싼 결정·리스크는 넣고, 구현 디테일·자명한 것은 AI용으로 내린다.
- **가정+표시**: AI가 인터뷰 답 없이 채운 결정은 반드시 "○○로 가정함 ← 맞나요?"로 `결정할 것`에 노출. (조용한 기정사실화 차단)
- **"안 하는 것"**: 경계 명시 → scope creep·구멍 방지.
- **결정거리를 수면 위로**: 진짜 결정거리를 자명한 사실처럼 평평하게 깔지 말고 `★` 섹션으로 끌어올려 레이더에 걸리게.

### 3.7 파일명 규칙 = `{이슈번호}-{slug}`

- 예: `12-service-status-page.md`, `12-service-status-page-backend.md`, `12-service-status-page-contract.md`
- `#`는 뺀다 (터미널 주석·URL 앵커 충돌). 번호만.
- 의도: **이슈 번호로 검색** + **이슈 순서로 정렬** 둘 다.
- 현재는 `<slug>.md` (번호 없음) → 전체를 `{번호}-{slug}` 로 변경.

## 4. 실증 근거 — `service-status-page` 해부 (왜 이 설계인지)

> 실제 Reclip의 기존 plan 산출물(`service-status-page`)을 운영자와 함께 해부한 결과. 이 설계의 근거다.

**사람용 원본**: 90%가 AI용 명세(엔드포인트·503·30초 폴링)인데 `requirements/` 자리에 앉은 잡탕. 운영자 GO 판단 바꿀 게 거의 없었음. → 운영자 반응: *"내용은 알겠는데 내가 왜 이걸 보고 있지?"*

**진짜 결정거리가 묻혀 있었음** (요구사항 사이에 평평하게 깔려 레이더에 안 걸림):
- 인증 없는 공개 엔드포인트 (정보 노출 판단)
- Frontend 레포 첫 출범 ("Next.js 초기 스캐폴딩 포함"이 괄호 안에 묻힘)
- DB 장애 상태(disconnected) 외부 노출

**AI용(backend) 해부 — 역설적 발견**:
- AI용 문서는 오히려 잘 쓰여 있음. → **현재 plan은 AI용은 잘 쓰고 사람용은 못 쓴다.** LLM은 구현 명세는 잘하지만 "사람이 결정할 것을 가려 띄우는" 추상화를 안 한다. → 두 층 분리 + ④사람용 파생 + ⑤정합성critic이 정확한 처방.

**위험 메커니즘 실물 포착** (= "나 모르는 새 이상하게 제작"의 정체):
- AI용에 `인증 없이`가 **결정이 아니라 기정사실로** 박혀 있음. 운영자 승인 없이 명세로 굳음 → 자동 회로가 충실히 구현. → ⑤ critic 역할 확장 + 가정+표시의 근거.

**구멍 실물**:
- 공개 엔드포인트인데 **rate limiting이 사람용·AI용 양쪽 다 없음.** 누구나 무한 호출 → DB 타격. ③ 완결성 critic이 있었으면 잡았을 전형적 보안 구멍.

**사람용 재작성 예시 (After)** — 원본보다 짧으면서 30초 안에 "결정할 건 이 3개"가 보이고, rate limiting 구멍이 "가정 ← 맞나요?"로 표면화됨:
```markdown
# 12 서비스 상태 페이지

## 한 줄
서비스 살아있는지 외부 공개로 보여주기 + 파이프라인 3영역 동시 검증 첫 실전.

## 당신이 결정할 것
- ★ 인증 없는 공개 엔드포인트 — 버전·DB상태 누구나 봄. 노출 OK?
- ★ Frontend 레포 여기서 첫 출범 — 지금 시작 맞나?
- rate limiting "없음"으로 가정함 ← 맞나요?

## 이번에 안 하는 것
- 인증/로그인, 알림, 과거 상태 이력

## 키 피처
- 공개 /status 페이지 + Admin 상태 카드

## 리스크 / 미정
- "현재 UTC 시각" 응답 용도 불명

## 상세 명세 → plans/12-service-status-page-*.md
```

## 6. Pipeline 고유 고려사항

### 6.1 "큰 결정 체크리스트" 4항목 평가 (CLAUDE.md 강제)

### 6.2 새 config / 카탈로그 항목 후보 (즉흥 이름 금지 — 카탈로그에 먼저 추가)

- 현재 `plan.md.tmpl`은 이미 `oh-my-claudecode:planner` / `oh-my-claudecode:deep-interview`를 호출한다(=OMC 의존 전제). critic도 `oh-my-claudecode:critic` 재사용을 가정.

## 7. 후행 과제 — SSOT(ARCHITECTURE) 수렴 자동화 (post-merge, 별도 기능)

> **이건 본 작업(plan 고도화)과 별개의 후속 기능이다.** plan 고도화가 먼저 돌아 `contract.md`가 생산돼야 입력이 생기므로 **자연히 후행**. 단 운영자가 "이 일관성 유지 아이디어"를 매우 중시하므로 반드시 기록해 둔다.

**개념**: 계약 문서를 일회성으로 버리지 않고, 구현 완료 후 프로젝트 SSOT(예: `ARCHITECTURE.md`)에 **수렴**시킨다. 그러면 다음 피쳐 plan의 ②a(코드베이스 흡수)가 갱신된 진실을 참조 → **일관성이 누적**되고 **표류가 차단**된다.

```
새 피쳐 plan ②a 에서 기존 SSOT 흡수 → 일관된 계약 작성
  → 구현 완료(머지) 후 실제 코드에 맞춰 SSOT 갱신 (표류 차단)
  → 다음 피쳐 plan 이 갱신된 진실 참조 (일관성 누적)
```
- 핵심: "계약 N개 누적"이 아니라 **"SSOT로 수렴 후, 기능 계약은 스냅샷으로만 남김"**. 진실은 항상 SSOT 한 곳.

**자동화 설계 (구현 시)**:
- 트리거: parent의 모든 영역 sub-issue가 Status=Done 된 시점 (`merge.yml` 또는 App chain 확장)
- 입력: 머지 diff + 그 기능의 `contract.md`
- 처리: AI가 "아키텍처적으로 의미 있는 델타"만 추출 → SSOT 갱신 PR 자동 생성
- **게이트: 사람 리뷰 필수** (SSOT 오염 방지, 완전 무인 금지 — plan의 사람 게이트 철학과 동일)
- 난점: "아키텍처적으로 의미 있는 변경"만 가려내기 (구현 디테일 제외 → 노이즈 PR 방지)
- 위험: SSOT 오염 / SSOT 비대화 / 여러 기능 동시 갱신 충돌
- 채택: §2 기본값 C — 무거운 기능이라 "능동 제안으로 확인" 대상
- **본체 종속성 주의**: "SSOT가 `ARCHITECTURE.md`라는 것"은 프로젝트 고유 → `architecture-ssot-path` config로 주입. 메커니즘만 본체.

## 8. 그쪽에서 판단/결정할 미해결 질문

1. **인터뷰 구현 방식**: § 3.3 7구간 대본을 (a) 기존 `deep-interview` 스킬에 대본을 주입해 재사용할지, (b) plan 자체 인터뷰 루틴으로 구현할지. (운영자는 deep-interview를 이미 많이 써서 "다른 방법론 기반"을 원함 — 단 "스킬을 안 쓴다"가 아니라 "질문 대본이 달라야 한다"는 뜻)
2. **critic 호출 비용/시점**: ③⑤를 매 plan마다 돌리면 자동 회로가 느려진다. ~~단일 1패스 시작~~ → **§0.5 D1로 갱신**(③단일·⑤이중 비대칭). 남은 미정: ⑤ 이중 critic을 config 토글로 끌 수 있게 할지(비용 회피).
